# 说说与 md_note 仓库双向同步 — 设计文档

- **日期**: 2026-11-03
- **状态**: 已通过评审（实现计划：`docs/superpowers/plans/2026-11-03-moment-two-way-sync.md`）
- **修订**: v1
- **关联**: `2026-09-21-github-note-sync-design.md`（笔记 → 文章的单向同步，本设计复用其 GitHub 客户端、调度器与配置）

## 1. 目标

让博客「说说」（`moment` 表）与笔记仓库 `Ryu2u/md_note` 根目录下的 `说说/` 文件夹**保持对齐**：

- 在仓库里新增、修改、删除 `说说/*.md`，博客里的说说随之新增、修改、删除
- 在后台发布、修改、删除说说，仓库里的文件随之新增、修改、删除
- 两边同时改了同一条时，**以仓库为准**
- 文件格式对手写友好：最简单的说说就是一个纯文本文件（文件名是发布时间），和现在仓库里已有的 `说说/2026_09_17_22_15.md` 一致

## 2. 非目标

- **不做实时同步**：后台改动在下一轮定时同步（`NOTE_SYNC_INTERVAL_MIN`，默认 30 分钟）才写回仓库，不改动后台现有接口
- **不同步点赞数、评论数**：它们是服务器计数，不进文件
- **不处理文件改名**：后台不能改说说的发布时间，所以文件名稳定；仓库里把文件改名会被看作「删一个、增一个」
- **不做冲突界面**：冲突按固定规则（仓库为准）处理，不提供手动解决入口
- **不支持多实例后端**：和现有笔记同步一样，调度器假定只有一个后端进程在跑
- **不改笔记 → 文章的既有行为**：只有两处结构性改动——「拉树」提到调度层、笔记过滤排除说说目录（见 §4），笔记同步的结果不变
- **不在后台新增同步状态页面**：只在「说说」页加一行说明文案

## 3. 已确认的决策

| 问题 | 决定 |
|---|---|
| 对齐到什么程度 | **双向同步**：仓库来的说说照常同步，后台手动发的说说也写回仓库 |
| 两边都改了听谁的 | **仓库为准**，覆盖后台那份改动，并把被覆盖的后台内容写进 warn 日志（见 §7.4） |
| 文件里怎么表达图片 / 位置 / 是否公开 | **纯文本 + 可选文件头**：默认纯文本；有位置或私密时才写 YAML 文件头；图片以 Markdown 图片行写在正文末尾 |
| 后台改动何时写回 | **随下一轮定时同步**，不在保存时推送 |

注意这与现有笔记同步**方向相反**：笔记同步遇到冲突是「本地赢、标记冲突并跳过」（`apply_update`），说说是「仓库赢」。这是有意的，不要为了统一而改成同一种。

## 4. 架构概览

```
src/note_sync/
├── moment_sync.rs     # 新增
│     纯函数：文件名 ↔ 发布时间、文件解析 / 渲染、认领匹配、差分规划（可直接单测）
│     带 IO：拉取阶段、写回阶段、一轮说说同步入口
├── github_client.rs   # 新增 put_file / delete_file；新增错误 Forbidden、Conflict；API 根地址可配置
├── scheduler.rs       # 一轮里只拉一次仓库树，依次交给笔记阶段与说说阶段
├── sync_engine.rs     # run_sync_cycle 拆出「拉树」；笔记过滤额外排除说说目录
└── structs.rs         # 新增 MomentSyncMap
src/moment/mod.rs      # serialize_images / parse_images 提到这里供同步复用
schema.sql             # 新增 moment_sync_map 表
```

要点：

- **只拉一次树**。`GithubClient` 把 ETag 缓存在实例上，同一轮里第二次 `list_tree` 会得到 304 而拿不到条目，所以必须由调度层拉一次，再把条目分别交给两个阶段。
- **树没变（304）时**：笔记阶段与说说的拉取阶段都跳过；**说说的写回阶段照常执行**，因为后台改动不会让仓库树变化。写回阶段只依赖映射表里记录的 `blob_sha`，不依赖这一轮的树。
- **一轮的顺序**：笔记阶段 → 说说拉取阶段 → 说说写回阶段。先拉后推，保证「仓库为准」的判断先于写回生效。
- **笔记过滤要排除说说目录**。`filter_entries` 现在只按 `NOTE_SYNC_ROOT` 前缀过滤；若有人把 root 配成空（整个仓库），说说文件会被当文章同步，所以要显式排除说说目录前缀。
- 总开关沿用 `NOTE_SYNC_ENABLED`；`false` 时说说同步也不运行。

## 5. 数据模型

### 5.1 新表 `moment_sync_map`

```sql
CREATE TABLE `moment_sync_map` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `moment_id` INT NOT NULL,
  `github_path` VARCHAR(512) NOT NULL,
  `blob_sha` CHAR(40) NOT NULL,
  `local_sha` CHAR(64) NOT NULL,
  `synced_at` BIGINT NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_moment_id` (`moment_id`),
  UNIQUE KEY `uk_github_path` (`github_path`(255))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='说说与仓库文件映射';
```

`schema.sql` 沿用既有的 `DROP TABLE IF EXISTS` + `CREATE TABLE` 写法；**迁移文档里必须用 `CREATE TABLE IF NOT EXISTS`**，不能带 DROP。

### 5.2 两个指纹

| 字段 | 含义 | 用途 |
|---|---|---|
| `blob_sha` | 上次同步时，仓库文件的 git blob sha | 与这一轮树里的 sha 比较 → 判断**仓库有没有变**；也是写回时 `put_file` / `delete_file` 带的旧 sha |
| `local_sha` | 上次同步时，`sha256(render(库里的说说))` | 与现在的 `sha256(render(库里的说说))` 比较 → 判断**后台有没有变** |

`local_sha` 来自「按库里数据渲染出的文本」，而不是仓库文件的原文。因此只要后台没改，就不会触发写回，**不会无故改写你手写的文件**（比如你的文件末尾没有换行、文件头顺序不同，都不会被机器重写）。

### 5.3 `moment` 表

不改表结构。同步只读写 `content` / `images` / `location` / `is_public` / `update_time` / `is_deleted`，以及新建时的 `created_time`；`likes` / `comments` 一律保持原值。拉取阶段更新说说时要**先读出整行、只改上述字段再 `update_by_column`**，不能用只含部分字段的结构体覆盖（`update_by_column` 会写全部列）。

## 6. 文件格式

### 6.1 文件名

- 格式 `YYYY_MM_DD_HH_mm.md`，时区固定 **+08:00**（代码里是常量，不做配置）
- 同一分钟已有文件：加秒数 `YYYY_MM_DD_HH_mm_ss.md`；仍重名，再加 `-2`、`-3`……
- 解析接受三种写法：`…_mm.md`、`…_mm_ss.md`、带 `-N` 后缀的版本
- **不符合格式的文件名**（如手写的 `随想.md`）也会同步：发布时间取该文件最后一次提交的时间（`last_commit_ms`），取不到则用当前时间
- 仓库里 `说说/` 下任意层级的 `.md` 都会被拉取；**新建文件一律写在 `说说/` 顶层**
- 排除目录沿用 `NOTE_SYNC_EXCLUDE_DIRS`（`.obsidian`、`.trash`），大小上限沿用 `NOTE_SYNC_MAX_FILE_KB`

### 6.2 文件内容

```
---
location: 南京
public: false
---
正文……

![](https://example.com/a.jpg)
![](https://example.com/b.jpg)
```

- **文件头只在「有位置」或「私密」时才写**。没有文件头就按公开、无位置处理
- 文件头是 `---` 包起来的逐行 `key: value`，不引入 YAML 库：只认 `location`、`public`；`public` 的 `false` / `0` / `no`（不区分大小写）表示私密，其余值表示公开；其他键忽略
- `---` 没有闭合：整个文件当正文
- 正文末尾的 `![任意alt](url)` 整行，被提取为 `images`。这些图片行之间**允许有空行**（Obsidian / Typora 粘贴出来的格式就是每张图隔一个空行），空行和紧挨着可以混用；从末尾往上遇到正文文字就停，夹在文字中间或位于开头的图片语法保留在正文里。带标题（`"t"`）或 url 含空白的不算图片行，会把更上面的图片隔断。2026-11-05 之前只识别紧挨着的图片行，图片之间有空行时只有最后一张被识别
- 解析时 CRLF 统一为 LF；正文首尾空白去掉
- 渲染时：有文件头则写文件头；正文；有图片则空一行再逐行写图片；文件以一个 `\n` 结尾
- **正文为空**（去掉首尾空白后）：不创建说说，只记 warn。对已映射的说说，文件被改成空也只记 warn，库里保持原样，不删除
- `images` 的规范化：库里的 `NULL`、空串、`[]`、无法解析的 JSON 都视为「无图」，保证指纹稳定

### 6.3 往返一致性

对任意说说 `m`，`parse(render(m))` 得到的 `(content, images, location, is_public)` 必须等于 `m` 规范化后的值。这是单元测试的核心属性。

唯一的例外：正文末尾恰好是独立的 `![](url)` 行（中间可以隔着空行）、而 `images` 为空时，往返后这些行会被识别为图片。渲染总是把图片写成紧挨着的规范形式，所以「空行分隔」与「紧挨着」两种写法解析出的结果相同。所以「内容是否相等」一律比较**两边各过一遍解析**的结果（`parse(render(说说))` 与 `parse(文件)`），而不是比较原文。这个边角只影响比较，不会丢数据。

## 7. 同步规则

### 7.1 一轮的流程

```
1. 调度层拉一次仓库树（ETag）
2. 笔记阶段（树变了才跑；逻辑不变）
3. 说说拉取阶段（树变了才跑）
4. 说说写回阶段（NOTE_SYNC_MOMENT_PUSH 为真时；树有没有变都跑）
```

### 7.2 拉取阶段（仓库 → 库）

候选文件：树里位于说说目录、`.md` 结尾、不在排除目录、不超过大小上限的 blob。

| 情形 | 动作 |
|---|---|
| 文件在库里**没有映射** | 先尝试**认领**（§7.3）；认领不到就**新建**说说，发布时间取自文件名（§6.1），`likes` / `comments` 为 0 |
| 有映射，文件 `blob_sha` 与记录**不同** | **仓库为准**：用文件内容覆盖说说的 `content` / `images` / `location` / `is_public`，`update_time` 取当前时间；之后刷新映射的 `blob_sha` 和 `local_sha`。如果这条说说在后台也改过（`local_sha` 与现在的指纹不符），先按 §7.4 记 warn |
| 有映射，文件变了，但**说说已被后台软删** | 仓库为准：说说恢复（`is_deleted = 0`）并更新 |
| 有映射，但库里**已没有这条说说** | 删除这条映射，按「没有映射」处理 |
| 有映射，**文件已不在树里** | 说说软删（已删则不动），删除映射 |
| 有映射，文件没变 | 不动 |

### 7.3 认领

目的：让库里**已存在**的说说（比如本地的 #1）与它在仓库里的对应文件绑定，而不是重复创建。

条件（同时满足才认领）：

1. 文件名能解析出时间，且与该说说的 `created_time`（换算到 +08:00）在**同一分钟**
2. 该说说未被软删、**还没有映射**
3. 文件内容与该说说**规范化后相等**：`parse(render(说说))` == `parse(文件)`（两边各过一遍解析，见 §6.3）

多个候选满足时取 `id` 最小的。认领后：写映射，`blob_sha` 取树里的 sha，`local_sha` 取现在的指纹；**不改说说内容**。

内容不相等就**不认领**，按新建处理：宁可出现两条同一分钟的说说，也不覆盖后台已有的内容。（这同时是「提交成功、写映射前崩溃」之后的收敛路径：文件内容就是库里那条说说渲染出的内容，下一轮会被认领回去。）

### 7.4 冲突与被覆盖内容的留存

「仓库为准」意味着后台那份尚未写回的改动会被**永久覆盖**——它从来没进过 git 历史，没有地方可以找回。缓解办法：发生覆盖时，warn 日志里写出说说 id、文件路径，以及被覆盖的旧内容（截断到前 500 个字符）。**只有两边规范化后的内容确实不同才记**：崩溃恢复（§7.6）时文件内容与库里一致，不应该误报。

### 7.5 写回阶段（库 → 仓库）

只处理已有映射、或需要新建文件的说说，按下面顺序，**每轮最多 50 个操作**，剩余的下一轮继续：

| 情形 | 动作 |
|---|---|
| 有映射，说说**已被软删** | `delete_file`（带映射里的 `blob_sha`）；成功或返回 404（文件已不在）后删除映射 |
| 有映射，说说未删，指纹与 `local_sha` **不同** | `put_file`（带映射里的 `blob_sha`）写入渲染文本；成功后用响应里的新 blob sha 更新 `blob_sha`，并更新 `local_sha` |
| 有映射，指纹相同 | 不动 |
| 说说未删、**没有映射** | 选一个文件路径（§6.1），`put_file`（不带 sha）；成功后写映射 |

因为拉取阶段先执行，任何「仓库也变了」的说说在到达写回阶段前，指纹已经刷新，不会被误推。

提交信息：`sync(说说): 新增 2026_09_18_19_40` / `更新 …` / `删除 …`。

选路径：先排除已知路径（映射表里的所有路径，加上这一轮树里的条目），在候选名里取第一个未占用的；`put_file` 返回「路径已存在」时换下一个候选，最多试 5 个。

### 7.6 崩溃安全

写回阶段的顺序是**先提交到 GitHub，再更新映射表**，任何一步中断，下一轮都会收敛：

| 中断点 | 下一轮发生什么 |
|---|---|
| 更新文件后、写映射前 | 仓库文件 sha 与映射里的不同 → 拉取阶段用同样的内容覆盖一次，结果不变 |
| 新建文件后、写映射前 | 文件在树里但无映射 → 认领把它绑回原说说 |
| 删除文件后、删映射前 | 文件不在树里、映射还在 → 说说本来就是软删状态，只清理映射 |

## 8. GitHub 客户端

### 8.1 新增方法

- `put_file(&mut self, path, text, message, sha: Option<&str>) -> Result<String, GhError>`：`PUT /repos/{repo}/contents/{path}`，body 含 `message`、`content`（base64）、`branch`，更新时带 `sha`；返回响应里的新 blob sha
- `delete_file(&mut self, path, sha, message) -> Result<(), GhError>`：`DELETE /repos/{repo}/contents/{path}`，body 含 `message`、`sha`、`branch`

两者都需要先确定分支（沿用 `branch()`）。

### 8.2 错误模型

| 响应 | 处理 |
|---|---|
| 401 | 沿用 `Unauthorized`：令牌失效 |
| 403，且是限流（响应头 `x-ratelimit-remaining: 0`，或正文含 `rate limit`） | 沿用 `RateLimited`：本轮写回停止，下轮重试 |
| 403，其他 | **新增 `Forbidden`**：日志提示「NOTE_SYNC_TOKEN 缺少 Contents 写权限」，**本轮写回阶段停止**；拉取阶段的结果不受影响 |
| 409 / 422 | **新增 `Conflict`**：旧 sha 对不上，或新建时路径已存在。这一条本轮跳过、不动映射；新建时则换下一个候选路径 |
| 网络错误 | 只跳过当前这一条 |

现有 `err_of` 把所有 403 都当成限流，读取场景没问题，写操作要用单独的映射函数区分。

### 8.3 API 根地址

`API_BASE` 常量改成客户端字段，默认 `https://api.github.com`，可由 `NOTE_SYNC_API_BASE` 覆盖。**非 https 只允许主机是 `localhost`、`127.0.0.1`、`[::1]`**，其他一律拒绝并回退默认值（带 warn）。这个口子只为本地用模拟服务做端到端测试。

## 11. 测试与验证

### 11.1 Rust 单元测试（纯函数）

- 文件名 ↔ 时间：+08:00 换算、跨午夜、`_ss` 与 `-N` 后缀、三种写法的解析、不符合格式的名字
- 路径选择：同一分钟重名、已知路径集合、多级后缀
- 解析与渲染：有 / 无文件头、`public` 各种取值、未闭合文件头、CRLF、图片行提取（只提取末尾那一段，行间允许空行，遇到文字就停）、空正文、往返一致（§6.3）、`images` 规范化
- 认领：同分钟且内容相等 → 认领；内容不等 → 不认领；多候选取最小 id
- 差分规划：§7.2 与 §7.5 表中的每一行都有用例，另加「两边都改」
- 笔记过滤排除说说目录（含 root 为空的情形）
- **变异检查**：把「仓库为准」改成「后台为准」、把认领的内容相等条件去掉，对应测试必须失败

### 11.2 端到端（不碰真实仓库）

临时 MySQL 库（用完删除）+ 本地 Python 实现的模拟 GitHub（树、contents 的 GET / PUT / DELETE，校验 sha，可切换为返回 403 / 409），跑发布版后端，`NOTE_SYNC_API_BASE` 指向模拟服务。场景：

1. 首轮：#1 被认领，#2 被写出为文件，映射正确，之后再跑一轮没有任何操作
2. 仓库里改文件 → 库里说说更新，点赞 / 评论数不变
3. 后台改说说 → 下一轮文件被更新
4. 仓库里新增文件 → 新建说说，发布时间取自文件名；不符合格式的文件名取提交时间
5. 后台新发说说 → 新建文件；同一分钟重名 → 带秒后缀
6. 两边删除：仓库删文件 → 说说软删；后台删说说 → 文件被删
7. 两边都改 → 仓库内容胜出，warn 日志含被覆盖的旧内容
8. 写权限 403 → 本轮写回停止，拉取照常，日志提示
9. 崩溃恢复：直接构造「文件已写入模拟仓库、但映射缺失（新建）或过期（更新、删除）」的状态，再跑一轮 → 收敛，没有重复说说，也不记误导性的 warn（对应 §7.6 三行）
10. `NOTE_SYNC_MOMENT_PUSH=false` → 只拉不写；`NOTE_SYNC_MOMENT_DIR` 留空 → 完全不动说说

### 11.3 真实仓库冒烟（需你明确同意）

会在 `md_note` 里产生提交，只有你明确说可以才做。上线建议见 §14。

### 11.4 前端

`tsc`、`npm run lint`（不得新增问题，现有 29 个）、`npm run build`，并在浏览器里确认说明文案显示正常。

## 12. 验收标准

- [ ] 在仓库 `说说/` 新增纯文本文件，下一轮后博客里出现这条说说，发布时间等于文件名里的时间
- [ ] 修改、删除仓库文件，博客里的说说随之更新、软删
- [ ] 在后台发布、修改、切换公开状态、删除说说，下一轮后仓库里的文件随之新增、更新、删除；点赞数与评论数不进文件
- [ ] 本地已有的 #1 被认领而不是重复创建；#2 被写成 `说说/2026_09_18_19_40.md`
- [ ] 两边都改同一条时，仓库内容胜出，旧内容出现在 warn 日志里
- [ ] 令牌无写权限时拉取照常，写回停止，日志有明确提示
- [ ] 稳定后重复跑多轮，不产生任何多余提交
- [ ] 笔记 → 文章的同步行为不变；`NOTE_SYNC_ROOT` 配成空时说说文件也不会被当文章
- [ ] `NOTE_SYNC_MOMENT_DIR` 留空即可完全关闭说说同步

## 13. 风险与已知限制

- **后台未写回的改动会被永久覆盖**：仓库为准，且这份改动从未进过 git。靠 §7.4 的 warn 日志留存
- **每个文件操作是一个提交**：Contents API 一次只能提交一个文件。首次同步会按「未映射的说说」数量产生提交；一轮最多 50 个，防止触发 GitHub 的二级限流
- **你本地的 Obsidian 副本会落后于远端**：后端写回后，需要先 `git pull` 再继续推送；本地和远端同时提交到不同文件通常能自动合并，改同一文件会产生 git 冲突
- **私密说说会写进仓库**：靠文件头 `public: false` 标记，仓库必须是私有的
- **时区固定 +08:00**：文件名里的时间按这个时区解释
- **按「同分钟 + 内容相等」认领**：同一分钟里有两条内容完全相同的说说时取 `id` 最小的，另一条会作为新文件写出
- **沿用现有限制**：GitHub 的递归树过大会被截断，现有代码不处理；「文件不在树里就软删」在截断时会误判。说说文件数量级很小，风险可忽略，但这是已知前提
- **仅单实例**：两个后端进程同时跑会重复写回
- **删除的恢复**：后台删说说会删除仓库文件，但文件在 git 历史里，可以从历史找回

## 14. 上线与运维说明

迁移文档（实现完成后另写）包含：

1. 备份 `moment` 表；用 `CREATE TABLE IF NOT EXISTS` 建 `moment_sync_map`
2. 确认 `NOTE_SYNC_TOKEN` 对 `md_note` 有 **Contents: Read and write**（fine-grained PAT）
3. 推荐分两步上线：
   - 第一步 `NOTE_SYNC_MOMENT_PUSH=false`，只拉取。看日志确认「认领 / 新建」符合预期
   - 第二步：先查询将被写出的说说（未软删、且不在 `moment_sync_map` 里的），确认后改成 `true`
4. 写回开始后，在本地 Obsidian 副本里 `git pull`
5. 回滚：`NOTE_SYNC_MOMENT_DIR` 留空即可停用；映射表和已写出的文件保留，不影响其他功能
