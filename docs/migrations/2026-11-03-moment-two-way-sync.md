## 0. 一分钟摘要

| 问题 | 答案 |
|---|---|
| 行为上改了什么？ | 博客的「说说」和仓库根目录 `说说/` 文件夹双向同步：仓库里新增/修改/删除文件，说说随之变化；后台发布/修改/删除说说，下一轮同步（默认 30 分钟）写回仓库。两边都改了同一条时**以仓库为准**。 |
| 要改表结构吗？ | **要新增一张表** `moment_sync_map`，`moment` 表不变。 |
| 要重新部署什么？ | **后端二进制** + **后台前端**（「说说」页多一行说明文案）。博客前端不用动。 |
| 要改 `.env` 吗？ | 不是必须（都有默认值），但**强烈建议第一次上线先加 `NOTE_SYNC_MOMENT_PUSH=false`**，见第 3 节。 |
| 令牌要什么权限？ | 写回需要 `NOTE_SYNC_TOKEN` 对该仓库有 **Contents: Read and write**（fine-grained PAT）。只有读权限也能用，但写回会被 403 拒绝，日志会提示，拉取不受影响。 |
| 最需要留意的风险？ | ① **后台未写回的改动会被仓库覆盖**，而且这份改动从没进过 git；② 写回会在你的仓库里产生提交，你本地的 Obsidian 副本需要 `git pull`；③ 私密说说也会写进仓库，仓库必须是私有的；④ **认领很严格**：库里已有的说说，只有内容、图片、位置、公开状态和仓库文件**全部一致**才会被绑定，有一项对不上就会按文件**再新建一条**，博客上出现重复，见 §2.4 与 §6。 |
| 第一轮同步只动说说吗？ | **不是**。一轮同步先跑笔记、再跑说说。`NOTE_SYNC_MOMENT_PUSH=false` 只关说说的写回，笔记那一半照常拉取，对新增或变更的笔记还会调用你配置的 AI 做分类。令牌过期了一段时间的话，第一轮会把期间的笔记变化一次补上，见 §3 第一步。 |
| 能回滚吗？ | 能。把 `NOTE_SYNC_MOMENT_DIR` 留空即可停用说说同步；映射表和已写出的文件保留，不影响其他功能。 |

## 1. 行为变化

| 场景 | 行为 |
|---|---|
| 仓库 `说说/` 下新增 `.md` 文件 | 新建说说；发布时间取自文件名 `YYYY_MM_DD_HH_mm.md`（+08:00）；文件名不规范则取该文件最后一次提交的时间 |
| 修改仓库里的说说文件 | 说说内容随之更新，点赞数、评论数保持不变 |
| 删除仓库里的说说文件 | 说说软删 |
| 后台发布说说 | 下一轮在仓库 `说说/` 下新建文件（文件名是发布时间，同一分钟重名加秒数） |
| 后台修改说说（含切换公开状态） | 下一轮更新仓库里的文件 |
| 后台删除说说 | 下一轮删除仓库里的文件（文件仍在 git 历史里，可找回） |
| 两边都改了同一条 | **仓库为准**，覆盖后台那份；被覆盖的后台内容（前 500 字）会写进后端的 warn 日志 |
| 库里已有的说说，与某个文件**同一分钟发布**，且**内容、图片、位置、公开状态全部一致** | 首次同步时被「认领」（绑定到该文件），不会重复创建，点赞数、评论数保留。**任何一项对不上都不认领**，而是按文件再新建一条（宁可重复，也不覆盖后台内容） |

文件格式：默认是纯文本；说说带位置或为私密时才有 YAML 文件头；图片以 Markdown 图片行写在正文末尾。图片行之间**可以有空行**（Obsidian / Typora 粘贴出来的就是每张图隔一个空行），也可以紧挨着，两种写法解析结果相同；程序写回时总是写成紧挨着的形式。每行只放一张图，写成 `![任意文字](地址)`，不能带标题（`"说明"`），地址里不能有空格，否则那一行不会被当成图片。

```
---
location: 南京
public: false
---
正文……

![](https://example.com/a.jpg)
```

## 2. 升级前

### 2.1 备份

```bash
mysqldump -u <用户> -p <库名> moment > /path/to/backup/moment_$(date +%F).sql
```

### 2.2 确认令牌权限

在 GitHub 的 fine-grained token 设置里，确认目标仓库（`md_note`）的 **Contents** 是 **Read and write**。不确定就先按第 3 节的两步上线：第一步只拉取，用不到写权限。

令牌有**有效期**。过期或被撤销后，GitHub 对它的所有请求都返回 `401 Bad credentials`，笔记同步和说说同步会一起失效，日志里是 `NOTE_SYNC_TOKEN 失效或过期，请在 .env 更换`。上线前先检查一下，令牌经标准输入交给 curl，不会出现在命令行参数里（在项目根目录执行）：

```bash
grep '^NOTE_SYNC_TOKEN=' .env | sed 's/^NOTE_SYNC_TOKEN=\(.*\)$/header = "Authorization: Bearer \1"/' \
  | curl -s -o /dev/null -w "HTTP %{http_code}\n" -K - https://api.github.com/rate_limit
```

返回 `HTTP 200` 才有效，`401` 就要重新生成：GitHub → Settings → Developer settings → Fine-grained tokens → Generate new token。**Repository access** 选 *Only select repositories* 并只选 `md_note`；**Permissions** 里只加 *Contents: Read and write*（*Metadata: Read-only* 会自动带上，其他都不用）。生成后立刻复制（页面刷新就看不到了），换掉 `.env` 里的 `NOTE_SYNC_TOKEN`，然后**重启后端**——`.env` 只在启动时读取。

### 2.3 建表

用 `IF NOT EXISTS`，**不要执行 `schema.sql` 里带 `DROP TABLE` 的那一段**：

```sql
CREATE TABLE IF NOT EXISTS `moment_sync_map` (
  `id` INT NOT NULL AUTO_INCREMENT,
  `moment_id` INT NOT NULL,
  `github_path` VARCHAR(512) NOT NULL,
  `blob_sha` CHAR(40) NOT NULL,
  `local_sha` CHAR(64) NOT NULL,
  `synced_at` BIGINT NOT NULL,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_moment_id` (`moment_id`),
  UNIQUE KEY `uk_github_path` (`github_path`(255))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='说说与仓库文件映射';
```

### 2.4 核对已有说说能不能被认领

库里已有的说说，要和仓库 `说说/` 下同一分钟的文件**完全一致**才会被认领（见第 1 节）。位置、图片、私密这几项最容易漏：文件是纯文本、库里那条却带着位置，就对不上，后端会按文件再新建一条重复的。

先列出库里哪些说说带了这些属性：

```sql
SELECT id, is_public, location, images, FROM_UNIXTIME(created_time / 1000) AS created, LEFT(content, 30) AS content
FROM moment
WHERE is_deleted = 0
  AND (is_public = 0
       OR (location IS NOT NULL AND location <> '')
       OR (images IS NOT NULL AND images NOT IN ('', '[]', 'null')))
ORDER BY id;
```

查出来的说说，如果仓库里已经有对应文件（发布时间同一分钟），就要二选一：把文件改成带文件头（`location:`、`public: false`）和图片行的样子（格式见第 1 节），或者在后台把库里的属性改成和文件一致。两边一致后再做第 3 节。仓库里没有对应文件的不用管，写回时会按库里的数据生成带文件头的文件。

## 3. 推荐的两步上线

### 第一步：只拉取，观察一轮

在服务器 `.env` 里加：

```
NOTE_SYNC_MOMENT_PUSH=false
```

部署新后端并重启，等第一轮同步（启动后约 10 秒）。**注意这一轮同时包含笔记同步**：`NOTE_SYNC_MOMENT_PUSH=false` 只关说说的写回，笔记那一半照常拉取、新建、更新，对新增或变更的笔记还会调用你在后台配置的 AI 做分类。令牌过期了一段时间的话，这一轮会把期间的笔记变化一次补上。想提前心里有数，可以对比仓库里的笔记文件和库里 `note_sync_map` 的 `github_path` / `blob_sha`，不一致的就是这一轮会动的。

看日志里的 `note_sync stats:` 和 `moment_sync:` 两行：

- `adopted` 是库里已有说说与仓库文件配对上的数量；
- `created` 是由仓库文件新建的说说数量；
- 不应出现意料之外的 `created`。库里已经有的说说被重复创建，说明认领条件没满足（同一分钟、内容、图片、位置、公开状态有一项对不上），处理见第 6 节。

### 第二步：打开写回

先看**哪些说说会被写成仓库文件**（还没有映射的、未删除的说说）：

```sql
SELECT m.id, m.is_public, FROM_UNIXTIME(m.created_time / 1000) AS created, LEFT(m.content, 40) AS content
FROM moment m
LEFT JOIN moment_sync_map s ON s.moment_id = m.id
WHERE m.is_deleted = 0 AND s.id IS NULL
ORDER BY m.id;
```

每条会在仓库里产生一个提交，一轮最多写 50 个，剩下的下一轮继续。确认无误后，把 `NOTE_SYNC_MOMENT_PUSH` 改成 `true`（或删掉这一行），重启后端。

写回开始后，在本地 Obsidian 副本里先 `git pull`，再继续写笔记：

```bash
cd ~/Documents/md_note && git pull
```

## 4. 升级后验证

1. 在仓库 `说说/` 下新建一个纯文本文件，如 `2026_11_03_20_30.md`，提交并推送；一轮同步后，博客「说说」页应出现这条，发布时间是 20:30；
2. 在后台「说说」页发布一条，一轮同步后仓库 `说说/` 下应出现对应文件；
3. 稳定后重复几轮，仓库里**不应再出现新的提交**；
4. 后端日志里的 `moment_sync:` 统计行，在没有任何改动时各项应全为 0。笔记那行 `note_sync stats:` 里如果每轮都有 `deleted=1`，通常是仓库里删过某篇笔记、库里留着它的映射，见第 6 节，不影响使用。

## 5. 回滚

- 停用：把 `.env` 里的 `NOTE_SYNC_MOMENT_DIR` 设为空，重启。说说与仓库不再同步，其他功能不受影响。
- 只想暂停写回：`NOTE_SYNC_MOMENT_PUSH=false`。
- 想换回旧后端二进制：旧版本不认识 `moment_sync_map`，直接忽略它，没有冲突。

## 6. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 日志：`NOTE_SYNC_TOKEN 缺少 Contents 写权限` | 令牌只读 | 给令牌加 Contents 读写权限；或先 `NOTE_SYNC_MOMENT_PUSH=false` |
| 日志：`仓库端已变化，本轮跳过` | 写回时仓库那一边刚好又变了 | 不用处理，下一轮会先拉取（仓库为准）再比较 |
| 日志：`仓库与后台都改了，以仓库为准` | 两次同步之间两边都改了同一条 | 被覆盖的后台内容在这行日志里；需要的话手动补回 |
| 本地 `git push` 被拒绝 | 后端往仓库提交过，本地落后了 | 先 `git pull` 再推送 |
| 说说文件被识别成了图片 | 正文末尾恰好有独立的 `![](url)` 行（可以隔着空行）且没有图片字段 | 这是文件格式的已知边角，不会丢数据；把这些行放到正文中间即可 |
| 说说里只显示了最后一张图，前面的图变成了一串文字 | 2026-11-05 之前的版本只识别末尾**紧挨着**的图片行，图片之间有空行时只有最后一张被识别 | 升级到 2026-11-05 之后的版本。**已经同步进库的残缺数据不会自动修正**：同步按「规范化后的内容」判断有没有变，旧版本留下的数据与文件解析结果规范化后相等，所以只改空白（比如末尾多一个空行）没用。修正办法二选一：对那个文件的**正文文字**做一处实际修改并提交，下一轮就会用文件覆盖库里的内容，图片也就拆对了；或者直接在后台编辑这条说说，删掉正文里残留的图片行，用上传把图片补回去 |
| 日志：`NOTE_SYNC_TOKEN 失效或过期，请在 .env 更换`（GitHub 返回 `401 Bad credentials`） | 令牌过期、被撤销或没复制完整；笔记和说说同步都会失败 | 按 2.2 重新生成令牌，换掉 `.env` 里的值，**重启后端** |
| 改了 `.env`（令牌、写回开关）没生效 | 后端只在启动时读取 `.env` | 重启后端 |
| 博客上同一条说说出现了两遍 | 认领没满足条件（内容、图片、位置或公开状态有一项和文件不一致），后端按文件又新建了一条 | ① 决定以谁为准，把库里那条或仓库文件改成一致；② 删掉多出来的那条及其映射（先用 `SELECT` 确认 id，别删带点赞数的原条）：`DELETE FROM moment_sync_map WHERE moment_id = <多出来的id>;` 再 `DELETE FROM moment WHERE id = <多出来的id>;`；③ 等下一轮或重启，统计应是 `adopted` 而不是 `created`。**写回开着时不要留着不一致**：没绑定的那条会被再写成一个新文件 |
| 从开发环境里启动后端，同步没跑 | 项目 `.claude/launch.json` 的 `backend` 配置带着 `NOTE_SYNC_ENABLED=false`，是开发时防止误同步用的，线上部署不受影响 | 直接 `cargo run`，或去掉那个配置里的 `NOTE_SYNC_ENABLED=false` |
| 笔记统计里每一轮都是 `deleted=1` | 仓库里删掉的笔记，库里的映射会一直保留，每一轮对已软删的文章再写一次 `update_time` | 已知，无害，不影响文章展示 |

## 7. 实测记录（2026-11-04）

在真实的 `md_note` 仓库上实测，数据都是测试数据。先用临时库验证全部行为，再在真实库上线。

### 7.1 临时库 + 测试目录（写回只落在 `说说-同步测试/`）

| 场景 | 结果 |
|---|---|
| 后台新发 | 下一轮在仓库新建文件；仓库树没变（304）时也会写回 |
| 后台修改 | 仓库文件被更新，提交信息 `sync(说说): 更新 …` |
| 仓库改文件 | 库里内容更新，点赞数不变，不会反向写回 |
| 两边同一周期都改 | 以仓库为准，仓库文件不被覆盖，被覆盖的后台内容写进 warn 日志 |
| 仓库新增带文件头 / 图片行的文件 | 新建私密说说，位置、图片 JSON 正确，发布时间等于文件名里的时间 |
| 仓库新增不规范文件名 | 新建说说，发布时间取该文件最后一次提交的时间（走真实的提交记录接口） |
| 后台删除 / 仓库删除 | 仓库文件被删 / 库里软删，映射清理 |
| 清理后多等一轮 | 没有任何多余的同步提交 |

没有在真实 GitHub 上测到的（进程内模拟的端到端测试覆盖过）：令牌无写权限（403）时停止写回、一轮最多写回 50 个、同一分钟重名。

### 7.2 真实库上线

1. 令牌已过期（401），重新生成后换进 `.env`。
2. 建 `moment_sync_map`（2.3）。
3. **第一轮只拉取**：笔记新建 1 篇、跳过 121 篇；说说本应认领第 1 条，却**新建了一条重复的**，因为库里第 1 条带着位置，仓库文件是纯文本，认领条件没满足（见 2.4、第 6 节）。重复的那条已撤回。
4. 把库里第 1 条的位置清掉，让两边一致后重跑：`adopted: 1, created: 0`，点赞数保留。
5. **打开写回**：`pushed_created: 1`，库里另一条没有对应文件的说说被写成 `说说/2026_09_18_19_40.md`，一次提交。
6. **冷启动再跑一轮**：说说统计各项全为 0，没有重复，没有多余提交。

测试期间在 `md_note` 里留下的提交：测试目录 `说说-同步测试/` 下 9 条（文件已全部删除，历史里还在），加真实 `说说/` 下的 1 条同步提交。
