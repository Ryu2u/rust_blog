# 迁移文档：同步文章默认全部展示

- **日期**：2026-11-02
- **适用对象**：已经部署了「GitHub 笔记同步」（`note_sync`）的服务器
- **前置版本**：可以直接叠加在「登录门禁」版本（见 `2026-11-02-login-gate-migration.md`）之上，也可以单独升级
- **配套文档**：设计文档 `docs/superpowers/specs/2026-09-21-github-note-sync-design.md`（修订 v2.4）

文中的 `<库名>`、`<服务名>` 等都是**需要你替换成自己环境的值**。

---

## 0. 一分钟摘要

| 问题 | 答案 |
|---|---|
| 行为上改了什么？ | 通过同步进来的文章**一律展示**。AI 的「是否可公开」判定只记录、不再决定展示；同步更新时也不会再改动文章的展示状态。**想取消展示，只能在后台「文章」页手动设置。** |
| 要改表结构吗？ | **不用。** 没有新表、新列。 |
| 要执行 SQL 吗？ | **要，一次性。** 之前被 AI 判为不可公开而隐藏的文章，需要执行第 4 节的那条 `update` 把它们改成展示（不执行的话，这些文章会一直保持隐藏，直到你在后台手动打开）。 |
| 要重新部署什么？ | **后端二进制**（核心）+ **后台前端**（仅「同步设置」页的一行说明文案）。博客前端**不用动**。 |
| 要改 `.env` 吗？ | 不用。 |
| 能回滚吗？ | 能。换回旧二进制即可；被改成展示的文章要恢复隐藏的话，见第 6 节。 |
| 最需要留意的风险？ | **AI 公开性审查这道闸门没有了**：笔记仓库里被 AI 判为含敏感内容的文章（隐私、凭据、公司机密、草稿碎片）今后也会展示。执行 SQL 前请先看第 3 节的清单，必要时把不该公开的文章排除掉。 |

## 1. 行为变化

| 场景 | 旧行为 | 新行为 |
|---|---|---|
| 同步**新建**文章 | 由 AI 判定决定 `is_view`；AI 判不可公开则隐藏；**AI 调用失败（降级）时默认隐藏** | **一律 `is_view = 1`（展示）** |
| 同步**更新**文章 | 仅当文章展示状态等于上次 AI 判定（后台没手动改过）时，才应用新的判定 | **绝不改动 `is_view`** |
| AI 判定为不可公开 | 文章被隐藏 | 只把判定与理由记到 `note_sync_map.ai_is_view` / `ai_reason`，**不影响展示** |
| AI 降级（调用失败、返回无法解析） | 兜底元数据带「不可公开」标记，文章被隐藏 | 兜底元数据不带任何不可公开标记，文章展示 |
| 想隐藏一篇文章 | 在后台手动改 | **只能在后台「文章」页手动设置**（这是唯一途径） |

> `note_sync_map.ai_is_view`、`ai_reason` 两列保留，供追溯「当时 AI 是怎么判的」，不参与任何逻辑。

## 2. 升级前

### 2.1 备份

```bash
mysqldump -u <用户> -p <库名> post note_sync_map > /path/to/backup/post_note_sync_map_$(date +%F).sql
```

### 2.2 确认服务器上有这两张表

```sql
show tables like 'note_sync_map';
```

没有输出，说明你的服务器没有部署过笔记同步，**这份迁移对你无事可做**，只需随常规升级换上新二进制即可，第 4 节的 SQL 也不用执行。

## 3. 先看清「将被改成展示」的文章

执行 SQL 之前，先用同样的条件做一次只读查询，确认这些文章你都愿意公开：

```sql
select p.id, p.title, m.path, m.ai_reason
from post p
join note_sync_map m on m.post_id = p.id
where p.is_view = 0 and m.ai_is_view = 0 and p.is_deleted = 0
order by p.id;
```

- **都可以公开** → 直接进入第 4 节。
- **有不该公开的** → 把它们的 `id` 记下来，在第 4 节的 SQL 末尾加上 `and p.id not in (<id1>, <id2>)`，这些文章会继续保持隐藏。
- **也可以先全部放开，再到后台把个别文章手动隐藏**——但那段时间它们是对读者可见的，不推荐。

另外记一下数量，第 5 节要对照：

```sql
select
  sum(p.is_view = 1) as shown,
  sum(p.is_view = 0) as hidden
from post p
join note_sync_map m on m.post_id = p.id
where p.is_deleted = 0;
```

## 4. 升级步骤

**顺序很重要：先换后端，再执行 SQL。** 这样新同步进来的文章从一开始就是展示状态，不会出现「SQL 刚改完，旧版同步又把新文章隐藏了」的情况。

### 第 1 步：构建并部署新后端

```bash
git pull
cargo build --release
# 重启后端（按你的方式；systemd 示例，Docker / supervisor 请换成对应命令）
sudo systemctl restart <服务名>
```

### 第 2 步：构建并部署后台前端

只有「同步设置」页的一行说明文案变了，**不换也不影响功能**，但建议一起换，免得页面上还写着旧规则。构建时仍需把写死的后端地址替换成线上地址，做法与登录门禁迁移文档的第 4 节第 4 步相同。

### 第 3 步：执行一次性 SQL

```sql
update post p join note_sync_map m on m.post_id = p.id
set p.is_view = 1
where p.is_view = 0 and m.ai_is_view = 0 and p.is_deleted = 0;
```

执行后会显示 `Rows matched: N  Changed: N`，N 应当等于第 3 节查询出的行数。

> **只执行这一次，并且要在你开始手动隐藏文章之前执行。**
> 这条语句靠 `ai_is_view = 0`（AI 曾判不可公开）来圈定对象。如果之后你在后台手动隐藏了一篇「AI 曾判不可公开」的文章，再跑一遍这条 SQL 会把它重新改回展示。

### 这条 SQL 的取舍

被圈定的是「当前隐藏」且「AI 曾判不可公开」的文章。旧版本里，**你在后台手动隐藏、且恰好 AI 也判过不可公开**的文章，和「纯粹被 AI 隐藏」的文章在数据库里无法区分，也会被一并改成展示。第 3 节的清单就是为此准备的——有这种情况请用 `not in` 排除。

- 隐藏中、但 `ai_is_view = 1`（AI 认为可公开，却是你手动隐藏的）→ **不受影响，保持隐藏**。
- 非同步来源的文章（不在 `note_sync_map` 里）→ **不受影响**。
- 已删除（`is_deleted = 1`）的文章 → **不受影响**。

## 5. 升级后验证

### 5.1 数据

重新跑第 3 节末尾那条统计，应满足：

- `hidden` 比升级前**减少 N**，`shown` 比升级前**增加 N**；
- 下面这条应返回 **0**（除非你用 `not in` 刻意排除了一些）：

```sql
select count(*)
from post p
join note_sync_map m on m.post_id = p.id
where p.is_view = 0 and m.ai_is_view = 0 and p.is_deleted = 0;
```

### 5.2 浏览器

1. 用一个读者账号登录博客，确认原先被隐藏的文章现在出现在列表里；
2. 后台「同步设置」页底部说明文案为：「所有同步的文章默认展示，AI 不会隐藏任何文章……」；
3. 在后台「文章」页手动把某篇同步文章改为不展示，等一轮同步（或重启后端后约 10 秒首轮）之后，确认它**仍然是隐藏的**——这证明同步更新不再改动展示状态。

## 6. 回滚

1. 换回旧的后端二进制并重启；
2. 数据库不需要结构回滚；
3. 若要把第 4 节第 3 步改成展示的文章恢复成隐藏：
   - 有第 2.1 步的备份：只恢复那两张表，或按第 3 节记下的 `id` 列表执行
     `update post set is_view = 0 where id in (<id 列表>);`
   - 没有记录 `id` 列表：用第 3 节同样的联表条件取不到了（现在它们都是展示状态），请从备份里查。

注意：旧二进制重新上线后，它会按旧规则处理**之后**新同步的文章（AI 判不可公开就隐藏、降级时默认隐藏）。
