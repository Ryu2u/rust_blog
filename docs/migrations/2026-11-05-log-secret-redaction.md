# 迁移文档：日志不再泄露数据库密码、用户密码和密码哈希

- **日期**：2026-11-05
- **适用对象**：所有已经部署了后端的环境（开发、测试、线上）
- **对应提交**：`ef54137`（`fix(log): 日志不再泄露数据库密码、用户密码、文章口令和密码哈希`）

文中的 `<日志位置>`、`<用户>` 等都是**需要你替换成自己环境的值**。

---

## 0. 一分钟摘要

| 问题 | 答案 |
|---|---|
| 行为上改了什么？ | 后端日志里不再出现：数据库连接的用户名和密码、请求体里的明文密码（新增 / 修改用户、文章口令）、写进库的 bcrypt 哈希、旧明文账号被改写时库里的明文密码。SQL 日志**仍然打印**，只是这些位置显示 `"***"`。 |
| 要改表结构吗？ | **不要**。 |
| 要改 `.env` 吗？ | **不要**。 |
| 要重新部署什么？ | **只有后端二进制**。前端不用动。 |
| 最需要做的是什么？ | **升级只管以后的日志，旧日志里已经有这些密码**。按第 2 节检查并处理已有的日志。 |
| 能回滚吗？ | 能，换回旧二进制即可，但旧版本会再次把这些内容写进日志。 |

## 1. 行为变化

| 日志里的内容 | 升级前 | 升级后 |
|---|---|---|
| `#[instrument]` 记录的 `db` 参数 | `db: Data(RBatis { … MySqlConnectOptions { username, password, … } })`，含数据库用户名和密码 | 不再出现，日志里只剩 `user`、`post`、`id` 等业务参数 |
| 新增 / 修改用户的请求体 | `User { …, password: "明文", … }` | `password: "***"`（盐也是 `***`） |
| 新增 / 修改文章的请求体 | `Post { …, password: Some("明文口令"), … }` | `password: Some("***")`，没设置口令时仍是 `None` |
| SQL 的绑定参数 | 全部原样打印，包括 bcrypt 哈希，以及旧明文账号被改写时原样绑回的明文密码 | 绑定到 `password` / `salt` / `ai_api_key` 列的参数，以及任何形如 bcrypt 哈希的字符串，显示为 `"***"`；其余参数原样 |
| 查询结果 | 只打印行数（开了 `debug_mode` 特性会打印整行） | 永远只打印行数 |
| SQL 日志行末尾的来源位置 | rbatis 的源码路径 | `src/utils/sql_log.rs`，只是显示不同 |

升级后 SQL 日志的样子（格式不变，只有敏感位置变成 `"***"`）：

```
[rbatis] [123] => `update tb_user set password = ? where id = ?` ["***",3]
[rbatis] [124] => `select * from tb_user where username = ?` ["alice"]
```

## 2. 升级后要处理：旧日志

升级之前写出的日志文件不会被改动。**只要旧日志里有，就要当作泄露处理。**

### 2.1 检查旧日志里有没有

`<日志位置>` 是日志文件或目录（后端默认输出到标准输出，具体看你的部署方式：systemd、Docker、nohup 重定向、日志收集平台等）。

```bash
# 数据库连接配置（含用户名和密码）
grep -rl 'MySqlConnectOptions' <日志位置>

# bcrypt 哈希（新增 / 修改用户、旧账号登录自动升级时写进 SQL 日志的）
grep -rlE '\$2[abxy]\$' <日志位置>
```

有命中的文件，就说明里面有对应的内容。

### 2.2 处理建议

| 情况 | 怎么做 |
|---|---|
| 数据库连接配置出现在日志里 | 视为数据库密码已泄露：**轮换数据库密码**。`ALTER USER '<用户>'@'<主机>' IDENTIFIED BY '<新密码>';`，再改 `.env` 里 `DATABASE_URL` 的密码，**重启后端** |
| 日志被转存过 | 日志平台、工单、截图、聊天记录里贴过的日志都算，一起清理 |
| bcrypt 哈希出现在日志里 | 哈希不是明文，风险较低，但泄露后可以离线爆破。弱密码的用户建议改密码 |
| 库里还有旧明文账号 | 见 2.3 |
| 管理员新增 / 修改用户时提交的密码 | 升级前，这些明文密码会被 `#[instrument]` 记进日志。涉及的用户建议改密码 |
| 文章口令 | 同上，设置过文章口令的文章，建议换口令 |

清理或归档旧日志，并限制谁能读。

### 2.3 旧明文账号

项目保留了旧明文密码的兜底：库里还存着明文密码的账号，在**登录成功时自动升级成 bcrypt**。在升级之前，这类账号的明文还会出现在：管理员不带新密码修改该用户时（库里原有的密码被原样绑回 `update`）。

先看库里还有没有：

```sql
SELECT id, username FROM tb_user WHERE password NOT LIKE '$2%' ORDER BY id;
```

有的话：让这些用户登录一次，自动升级成 bcrypt；同时按 2.2 通知他们改密码，因为明文可能已经在旧日志里。没有就不用管。

## 3. 升级步骤

1. 部署新后端并重启。无数据变更，不需要备份。
2. 按第 4 节验证。
3. 按第 2 节处理旧日志。

## 4. 升级后验证

在一个测试账号上（或测试环境），依次做：登录一个账号、新增一个用户、修改这个用户并改密码，然后搜日志：

1. 搜 `MySqlConnectOptions`：**应该搜不到**。
2. 搜 `$2b$`：**应该搜不到**。
3. 搜刚才提交的测试密码：**应该搜不到**。
4. 搜 `update tb_user set`：应该能看到这几条 SQL，密码位置是 `"***"`。
5. 搜 `select * from tb_user where username`：参数应该是完整的，如 `["alice"]`，说明普通 SQL 日志不受影响。

## 5. 回滚

换回旧后端二进制即可，无数据变更。注意旧版本会再次把数据库密码、请求体密码和哈希写进日志。

## 6. 开发者：以后新增接口或新增密钥列

这套规则写在 `CLAUDE.md` 的 Conventions 里，对应三层防护，都有测试：

| 层 | 规则 | 测试 |
|---|---|---|
| `#[instrument]` | 接收 `db: web::Data<RBatis>` 的函数必须 `skip(db)`（或 `skip(db, cos)`、`skip_all`） | `src/log_guard.rs`：漏了就失败，并指出文件和行号 |
| 带密码的类型 | `User`、`LoginDto`、`Post` 的 `Debug` 是手写的，密码输出 `***`；新增字段要同步加到 `Debug` 里 | 各类型的测试检查「每个序列化字段都被列出」 |
| SQL 日志 | `src/utils/sql_log.rs` 的 `RedactingLogInterceptor`，在 `init_rbatis` 里替换了 rbatis 默认的拦截器 | `src/utils/sql_log.rs` 里的测试，包括「默认拦截器不能被换回去」 |

新增了存放密钥的列（令牌、密码、密钥密文），**把列名加到 `SENSITIVE_COLUMNS`**，否则它的绑定参数会被打印（bcrypt 形状的值除外，那条是兜底）。

## 7. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 测试 `instrument_never_logs_the_database_handle` 失败 | 新增了接收 `RBatis` 的 `#[instrument]` 但没跳过它 | 按失败信息里的文件和行号，写成 `#[instrument(skip(db))]` |
| 测试 `user_debug_lists_every_serialized_field`、`post_debug_lists_every_serialized_field` 或 `login_dto_debug_hides_password` 失败 | 给 `User` / `Post` / `LoginDto` 加了字段，没改手写的 `Debug` | 把新字段加进对应的 `impl Debug` |
| 调试时想看被打码的参数 | 脱敏是故意的 | 不要关脱敏，用 SQL 客户端直接查库 |
| 新增了含密钥的列，日志里还是出现了明文 | 列名不在 `SENSITIVE_COLUMNS` 里，且值不是 bcrypt 形状 | 把列名加到 `SENSITIVE_COLUMNS` |
| SQL 日志里出现了 `"***"`，但那个参数不是密码 | 命中了兜底规则：长得像 bcrypt 哈希的字符串 | 正常，说明有哈希被绑定到了某一列 |
| 升级前保留在应用或日志平台里的旧日志仍含密码 | 升级不改动已有日志 | 按 2.2 处理 |
